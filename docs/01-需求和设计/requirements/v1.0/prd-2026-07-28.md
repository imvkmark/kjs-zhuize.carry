# 追责系统全端产品需求文档（PRD）

> **版本**：V1.5  
> **日期**：2026-07-28  
> **需求方**：产品  
> **需求状态**：待产品、研发、测试联合评审  
> **原型基线**：`追责系统全端产品原型（7.27）.html`  
> **涉及终端**：PC Web（追责前台、追责后台）、追责 H5、服务端  
> **使用者**：平台管理员、核赔/审核人员、团队管理员、追责组长、追责员、外访员、回访人员  
> **核心设计原则**：
> - 案件主状态、追责状态、追责结果、回访状态相互独立，不以页面展示状态替代业务状态。
> - 涉及身份、权限、会话、状态流转和敏感数据的最终判断必须由服务端完成。
> - 同一案件跨前台、后台、H5使用统一 `case_id`；同一业务字段必须单一来源、跨端一致。
> - 已提交的过程记录只可追加，不覆盖历史；关键操作必须可审计、可追溯。
> - 共案同步处理不覆盖各案件自身的金额、催记、追责结果、结案结果和历史记录。

# 第一章 需求概述

## 1.1 执行摘要

追责系统面向电商售后追偿业务，建设一套覆盖“订单转案—团队流转—人员分配—案件执行—催记/外访—两级审核—结案—客户回访—收款/退款—审计配置”的全链路协同平台。追责前台负责团队案件、个人作业、动态收款码和退款申请，追责后台负责任务流转、审核、回访、退款审核、标签及系统配置，追责 H5 支持移动端案件处理、收款进度、敏感信息申请和结案操作。系统通过统一案件与交易数据、状态约束、字段级授权、人脸验证、追加式历史记录和支付退款审计，降低跨角色信息断层、误分配、越权查看、收款不透明和过程不可追溯风险。

## 1.2 产品背景

售后追责涉及平台、外部追责团队、外访人员、审核人员和回访人员。原型体现的主要业务问题包括：

| 问题 | 业务影响 | 原型对应能力 |
|---|---|---|
| 分案与案件列表割裂 | 人员需要跨菜单查找同一案件，状态与负责人容易不同步。 | 前后台均将分案能力合并入“案件管理”的“待分配”页签。 |
| 案件过程跨团队流转复杂 | 团队、负责人、状态、关联案件容易被错误覆盖。 | 状态机、流转/回退、共案提示及二次确认。 |
| 结案信息与后续回访脱节 | 客户联系方式和结案结果无法稳定传递给回访人员。 | `follow_up_phone`、结案生成回访订单、追加式回访历史。 |
| 敏感信息暴露风险 | 手机号、地址、身份证和材料可能被无授权查看。 | 脱敏规则、权限申请、字段级授权、模块级展开。 |
| 账号共用与冒用风险 | 无法确认登录人与实名人员一致。 | 首次人脸采集、登录/结案人脸验证、失败限制和记录。 |
| 静态过程记录易被覆盖 | 无法准确还原案件处理、审批和回访过程。 | 历史进程、操作日志、验证记录、回访追加记录。 |
| 收款与退款分散 | 追责人员难以及时确认多次付款，退款申请与审核缺少闭环。 | 30分钟动态收款码、交易流水表、部分/全额退款、后台审核及H5案件级收款汇总。 |
| 风险特征和历史归属难识别 | 列表无法快速识别案件标签和历次售后处理责任。 | 标签字典、案件标签、多选筛选、历史售后快照和次数。 |

> 🔶 假设：当前没有提供真实用户调研、业务量或线上数据，本 PRD 的问题证据主要来自原型结构及变更日志。正式立项前应由运营补充基线数据和典型案例。

## 1.4 产品范围

### 1.4.1 本期范围

1. 统一登录、视图选择、账号中心及会话安全。
2. 前台团队案件、待分配、我的案件、催记、结案、外访申请和初审。
3. 后台案件流转、回退、包赔、关联关系、实锤、黑名单、查重和终审。
4. 结案后回访订单、统一回访状态、追加式历史记录和附件元数据。
5. 字段脱敏、全量/单字段敏感信息申请、后台授权和H5模块展开。
6. 首次人脸采集、登录/结案验证、失败保护、会话到期和验证记录。
7. 信函、审批流、组织、角色、用户、收款信息、团队业绩及操作日志。
8. 动态收款码、前后台交易流水、全额/部分退款申请、退款审核/驳回和H5案件级多笔收款汇总。
9. 后台标签字典、案件标签维护/筛选，以及案件详情历史售后快照与列表次数。
10. H5移动作业、分期跟进、审核进度、案件详情和个人中心。

### 1.4.2 后续范围

1. 真实人脸认证服务与活体检测SDK接入。
2. 真实IM、文件存储、病毒扫描、在线预览和下载服务。
3. 真实业务系统订单、支付回调、原路退款、签函、短信/电话与数据仓库接口。
4. 指标基线、运营看板口径和告警策略的生产化。

## 1.5 名词说明

| 名词 | 定义 |
|---|---|
| 案件 | 由售后订单转化的追责业务单元，以 `case_id` 唯一标识。 |
| 委案 | 将案件分配至某个追责团队的动作。 |
| 分配 | 团队内将案件分配给具体追责人员的动作。 |
| 案件状态 | 业务问题类型，如换号换绑、追回退款、平台赔付、买家恶意。 |
| 追责状态 | 案件所处处理阶段，如待委案、一手处理中、一手处理完成。 |
| 追责结果 | 案件处理结果，如分期还款中、已追回、未追回。 |
| 共案 | 存在同一追责目标或明确关联关系、需要协同分配的多个案件。 |
| 溯源链 | 围绕同一游戏账号的历史订单和卖家流转关系。 |
| 追偿目标手机号 | 结案时最终确认的联系手机号，保存为 `follow_up_phone`。 |
| 案件原始手机号 | 案件基础资料中的 `customer_phone`，不因结案手机号修改而改变。 |
| 回访订单 | 案件提交结案后生成的独立回访任务。 |
| 敏感字段 | 手机号、身份证、地址、账号材料等受权限控制的数据。 |
| 字段级授权 | 按申请人、案件和字段类型授予限时查看权限。 |
| 追加式记录 | 已提交内容不可修改或删除，每次只新增一条历史记录。 |
| 动态收款码 | 服务端签发、与案件及支付订单绑定且在30分钟后失效的收款入口。 |
| 交易流水 | 支付服务确认的一笔实际收款记录，以 `transaction_id` 唯一标识。 |
| 净收款 | 成功支付总额减去已完成退款总额；退款审核中不提前扣减。 |
| 退款申请 | 前台针对一笔已支付流水提交的全额或部分退款请求。 |
| 案件标签 | 后台统一维护、可多选绑定案件的风险或证据特征标识。 |
| 历史售后 | 案件在历史处理阶段形成的团队、负责人和完成状态快照。 |

| 密码 | 登录密码。 | 不能为空；传输和存储不得明文。 | 是 |
| 登录视图 | 追责前台或追责后台。 | 登录成功后进入所选视图并同步顶部视图切换器。 | 是 |

1. 账号密码通过后，若 `normal_login_face_enabled=false`，直接创建会话并进入所选视图。

## 3.2 人脸采集、验证与会话

### 默认配置

| 字段 | 默认值 | 业务作用 |
|---|---:|---|
| `session_duration_hours` | 48 | 单次登录会话最长有效时长。 |
| `face_failure_limit` | 3 | 统计窗口内允许的计次失败上限。 |
| `face_failure_window_minutes` | 15 | 连续失败统计窗口。 |
| `face_lock_duration_minutes` | 30 | 达到上限后的限制时长。 |
| `normal_login_face_enabled` | `true` | 普通登录是否验证人脸。 |
| `h5_close_face_enabled` | `true` | H5提交结案前是否验证人脸。 |
| `h5_close_failure_action` | `keep_session` | 结案失败上限后的处理措施。 |

### 验证流程

```text
账号密码通过
  │
  ├─ 未完成人脸采集 → H5补充信息 → 提交 → 当前登录失效 → 重新登录
  │
  ├─ 配置为不验证 → 创建会话 → 进入系统
  │
  └─ 配置为验证 → 检查是否锁定
                    ├─ 已锁定 → 提示可重试时间
                    └─ 未锁定 → 人脸验证
                               ├─ 通过 → 创建会话
                               └─ 失败 → 记录结果/累计次数/必要时锁定
```

### 失败计数规则

| 分类 | 原因 | 是否计入失败次数 |
|---|---|---|
| 生物特征/采集失败 | 人脸不匹配、活体检测失败、未检测到人脸、光线不足、画面模糊、摄像头不可用 | 是 |
| 非用户身份失败 | 网络异常、系统异常、用户取消、服务超时 | 否 |

### 会话规则

1. `session_started_at` 和 `session_expires_at` 由服务端生成。
2. 到期后所有业务接口返回会话失效，前端清理本地状态并返回登录页。
3. H5提交结案验证失败时不得生成结案结果；达到上限后按配置保留登录或强制退出。
4. 前后台“人脸验证记录”共用同一页面，只展示当前账号记录。
5. 失败记录数量同步为两个菜单入口的红色角标。

### 模块规则

| 模块 | 能力 | 关键约束 |
|---|---|---|
| 敏感信息申请 | 全量申请或单字段申请。 | 申请后留在当前页；处理中禁用；后台通过后按范围展示。 |

## 3.4 通用异常处理

| 异常场景 | 处理方式 |
|---|---|
| 会话失效 | 中止当前写操作，保存可恢复草稿（如适用），返回登录页。 |
| 无页面权限 | 不展示菜单；直接访问接口返回403并记录审计。 |
| 数据范围越权 | 返回无权限，不返回目标案件任何敏感数据。 |
| 敏感权限不足或已过期 | 页面继续展示脱敏值或模糊占位；敏感字段、IM正文及附件接口返回无权限，不得先返回完整数据再仅由前端隐藏；允许按现有流程重新申请。 |
| 通用写操作重复提交 | 使用业务幂等键返回首次受理结果，不重复生成案件、回访历史、动态收款码或其他业务记录。 |
| 状态已变化 | 返回最新状态和冲突提示，要求刷新后重试。 |
| 文件上传失败 | 保留表单内容，标识失败文件，允许单文件重传。 |
| 网络失败 | 不假定成功；写操作支持查询最终状态。 |
| 支付回调验签失败 | 拒绝入账，保留必要的失败日志并触发安全告警；不得更新交易成功状态、案件收款汇总或案件状态。 |
| 支付回调处理失败 | 记录回调原始标识和失败原因，进入服务端重试或人工对账；客户端刷新时仍以服务端最终交易状态为准。 |
| 支付回调重复到达 | 以支付渠道、三方流水号和幂等键识别同一交易，返回已处理结果，不重复入账或累计收款。 |
| 退款申请重复提交 | 同一交易存在有效待审核申请时返回原申请，不重复冻结可退金额；已驳回后重新申请必须生成新的申请记录。 |
| 退款执行失败 | 将本次申请标记为“退款失败”，不得标记为部分退款或已退款，也不得提前扣减案件净收款；保留申请、审核人、失败原因和渠道结果，进入重试或人工处理。 |
| 退款结果回调重复 | 以退款单号和渠道退款流水号幂等更新，只允许首次有效结果改变累计退款金额。 |

上述异常均应返回稳定的业务错误标识、用户可理解的提示和可追踪的请求编号；具体错误码由接口设计阶段统一定义。

| 类型 | 字段 |

### 标签与历史售后

1. 标签筛选位于原搜索栏内；下拉为单列、可滚动，多选后在输入区域回显彩色标签。
2. 标签下拉打开时必须位于订单表格和固定列上方，不得被筛选卡片的 `overflow` 裁剪。
3. 列表行悬停仅显示该案件的彩色标签名称，不显示标签说明。
4. “历史售后次数”位于“关联案件”右侧，读取当前案件历史售后快照条数，显示“X次”。
5. 标签、历史售后次数均为关联数据的派生展示，不得写回或覆盖案件主状态。

### 关联案件数量展示

1. “关联案件”列与“分配追责人员”弹窗必须读取同一份已确认共案数据。
2. 当前订单存在共案时，列表显示“X个关联”；数量为去重后的关联案件数，不包含当前案件。
3. 当前订单无共案数据时显示“—”，不得根据详情页通用展示数据推算关联数量。
4. 有共案时，列表数量、首次分配提示和确认分配二次确认中的案件集合必须一致。
5. 服务端列表建议返回派生字段 `co_case_count`；打开分配弹窗时返回相同版本的共案成员、历史团队和历史负责人。

### 分配追责人员弹窗

| 元素 | 说明 | 校验 | 必填 |
|---|---|---|---|
| 当前团队 | 案件所属团队。 | 只能选择当前账号有管理权限的团队；选项格式为「华东追责/华南追责/西南追责/西北追责」。 | 是 |
| 追责人员 | 多选团队成员。 | 支持为案件同时分配多名追责人员。 | 是 |
| 处理时效 | 本次任务截止时间。 | 不得早于当前时间，不得超过团队委案时限。 | 是 |
| 备注 | 分配补充说明。 | 长度建议≤500字。 | 否 |
| 共案提示 | 共案数量、编号、历史团队、历史负责人。 | 仅单件且存在共案时展示。 | — |

### 分配业务规则

1. 分配成功后写入 `team_id`、`owner_id`、`assigned_at`、`due_at`。
2. 案件从“待分配”移出，进入“团队案件”，并同步至目标人员“我的案件”。
3. 菜单和“待分配”Tab角标使用同一未分配数量，成功后同步更新；为0时隐藏。
4. 批量分配必须对所有选中案件执行权限、状态和团队一致性校验。
5. 存在共案时先展示历史分配信息；首次确认后弹出“该订单存在共案，是否确认分配”。
6. 两级弹窗必须读取同一份服务端共案数据，二次确认后在同一事务中写入可同步案件。
7. 不可同步的共案返回案件编号和原因，不得静默跳过。

| 联系结果 | 接通承诺、未接通、拒绝配合、协商中、已追回等。 | 枚举由后端返回。 | 是 |
| 沟通内容 | 本次沟通摘要。 | 建议≤2000字。 | 是 |
| 上传附件 | 图片、音频、视频等。 | 类型、大小和数量由文件策略控制。 | 否 |

### 提交结案弹窗

| 字段 | 说明 | 业务规则 | 必填 |
|---|---|---|---|
| 案值金额 | 当前案件金额，只读。 | 打开弹窗时按当前 `case_id` 读取。 | 是 |
| 追偿目标手机号 | 本次结案确认的联系手机号。 | 初始值与详情当前展示值一致；可编辑；保存为 `follow_up_phone`。 | 是 |
| 追责结果 | 未追回、还号换绑、已追回、分期还款。 | 决定后续金额和分期字段。 | 是 |
| 追回金额 | 本次已追回金额。 | 已追回/分期时必填；不得小于0。 | 条件必填 |
| 违约金 | 线下已追回或分期场景的违约金。 | 不计入案件原始金额。 | 否 |
| 分期计划 | 期数、还款时间、还款金额。 | 分期时必填；期数与明细数一致。 | 条件必填 |
| 地理位置 | 当前IP/基站位置自动识别结果，只读。 | 所有追责结果统一展示；用户不能输入或修改，提交时由可信终端能力或服务端记录。 | 系统生成 |
| 附件/备注 | 证据和补充说明。 | 按结果类型校验附件要求。 | 条件必填 |

地理位置区域必须显示“该字段提交时隐藏，只能查看，不能编辑”。前端结案请求不得接受用户自行填写的位置文本；静态原型仅展示模拟识别结果。

### 保存案件

提交结案弹窗底部按钮栏包含三个操作按钮：取消、保存案件、提交外访结案。

1. 保存案件：将当前弹窗中已填写的追责结果、金额、手机号、分期计划、附件和备注写入服务端，但不触发审核流程。
2. 保存后弹窗不关闭，用户可继续编辑后提交或直接关闭。
3. 已保存数据在下次打开同一案件结案弹窗时回填。

### 追偿目标手机号规则

```text
案件 customer_phone
→ 按当前用户权限生成详情展示值
→ 同步到结案弹窗
→ 用户保留或修改
→ 保存 follow_up_phone + phone_modified
→ 前后台审核展示追责电话
→ 后台回访管理优先使用
```

1. 有完整手机号权限且未修改：保存完整号码。
2. 无权限且未修改脱敏文本：前端不得提交星号文本，服务端读取案件底层原始手机号。
3. 用户开始编辑后：必须填写完整有效手机号，且不得包含星号、空格、中文或非数字字符。
4. 修改 `follow_up_phone` 不得反向覆盖 `customer_phone`，也不代表获得原始号码查看权限。
5. 切换案件时必须重新读取当前案件数据，不得保留上一案件号码。

## 4.4 前台案件进度审核

### 页面目标

团队组长对追责员提交的处理结果进行初审，通过后进入后台终审，驳回后退回原追责人员。

### 审核弹窗

| 区域 | 展示/操作 |

| 催记记录 | 时间、追责员、方式、结果、内容、附件。 |
| 审核备注 | 驳回时必填，通过时选填。 |
| 操作 | 取消、审核驳回、审核通过。 |

### 业务规则

1. “追责电话”只读，读取结案保存的 `follow_up_phone`。
2. 审核通过时记录审核人、时间和意见，推送后台案件进度审核。
3. 审核驳回时必须填写原因，案件回到提交人待修改状态。
4. 审核操作不得修改回访订单或案件原始手机号。

  「全部案件」追责结果筛选Tab含「全部/—/分期还款中/未追回/已追回/资损」六项。

3. 可流转共案应分配至同一追责人员；已结案、团队冲突或状态不合法案件跳过并展示原因。
4. 同步只更新本次允许的团队/负责人/流转批次，不覆盖案件结果、催记、结案和历史。
5. 🔶 假设：真实后端应以共案组版本号加事务锁防止多人同时流转。

## 5.3 后台案件进度审核

### 页面目标

接收前台初审通过的一手、二手和线下处理结果，执行平台终审。

### 审核规则

### 提交规则

1. 回访人员自动读取当前登录用户名，只读展示。

7. 回访状态不加入案件状态机，回访异常不自动改变已结案案件状态。

### 授权边界

授权键至少包含 `applicant_id + case_id + field_type`。通过后合并既有授权范围，不覆盖先前已授权字段；到期或收回后服务端停止返回完整值。

IM消息使用独立敏感类型 `im_messages`，申请来源为 `case_detail_drawer_im`。未授权时，后端不得返回三个群聊的消息正文、附件真实地址或可发送凭证；同一案件授权通过后，交易售后群、卖家售后群和交易群共同解除读取限制，但发送能力仍按群类型和动作权限判断。

案件详情顶部“申请敏感信息权限”的全量申请必须包含 `im_messages`；若当前用户、当前案件已有包含该类型的待审批申请，不得重复创建独立IM申请。

## 5.9 后台交易流水与退款审核

后台交易流水表与前台读取同一交易及退款申请数据，但数据范围和操作权限独立校验。

```text
┌──────────────────────────────────────────────────────────────┐
│ 交易流水表：交易笔数｜收款总额｜待审核退款｜已退款            │
│ 搜索字段｜关键字｜支付渠道｜查询｜重置                       │
├──────────────────────────────────────────────────────────────┤
│ 交易与退款时间线                                      [审核] │
└──────────────────────────────────────────────────────────────┘
```

| 区域 | 需求 |
|---|---|
| 搜索/列表 | 字段与前台交易流水表一致，支持指定表头或全部字段搜索。 |
| 操作列 | 仅 `refund_status=待审核` 显示【退款审核】；未申请显示“暂无退款申请”；已驳回、退款处理中、退款成功或退款失败时显示对应结果。 |
| 审核弹窗 | 只读展示交易字段、申请人、申请时间、退款原因、退款金额和退款类型。 |
| 确认退款 | 写入审核人和审核时间，将 `refund_status` 更新为“退款处理中”，再由后端幂等调用退款渠道；此时不得提前填写退款完成时间或扣减净收款。 |
| 驳回 | 二次确认后写入驳回人、驳回时间和结果；不修改支付结果、实收金额或已完成退款金额。 |

退款审核状态流转：

```text
未申请
  → 待审核
     ├─ 驳回 → 已驳回 → 前台重新申请 → 新的待审核
     └─ 审核通过 → 退款处理中
                      ├─ 渠道成功 → 退款成功
                      └─ 渠道失败 → 退款失败
```

渠道成功后才写入退款完成时间和累计已退款金额，并按累计退款结果将 `payment_status` 更新为“部分退款”或“已退款”。渠道失败时保持原支付结果和净收款不变，记录渠道错误码及失败原因，支持按同一退款申请幂等重试或转人工处理。

### 收款进度卡片

收款进度位于地址信息下方、快捷图标上方。多次付款只显示案件级汇总，全部流水进入明细抽屉。

```text
┌──────────────────────────────────┐
│ 案件编号       处理状态    应收额 │
│ 收款进度 [部分收款]         共2笔 │
│ 已收/应收  █████░░░  27%         │
│ 剩余待收｜最近到账    [查看明细] │
│ 最后更新｜新到账                    │
│ 联系｜权限｜导航｜日程｜收款码     │
└──────────────────────────────────┘
```

| 元素 | 展示/规则 |
|---|---|
| 收款状态 | 未收款、部分收款、已收齐、超额收款；存在退款中或已退款流水时额外显示“存在退款”。 |
| 金额汇总 | 净已收、应收、剩余待收、付款笔数、收款比例。 |
| 最近到账 | 最近成功支付时间、渠道和金额。 |
| 刷新信息 | 最后更新时间；发现新支付时显示“新到账”。 |
| 查看明细 | 打开当前案件的支付流水抽屉。 |

状态与计算口径：

```text
累计支付 = 当前案件支付成功流水的 paid_amount 合计
累计退款 = 当前案件已完成退款的 refunded_amount 合计
净收款 = max(累计支付 - 累计退款, 0)
剩余待收 = max(应收金额 - 净收款, 0)

净收款 = 0              → 未收款
0 < 净收款 < 应收金额   → 部分收款
净收款 = 应收金额        → 已收齐
净收款 > 应收金额        → 超额收款
```

退款审核中只显示“存在退款”，不提前扣减净收款。付款比例的展示上限为100%，超出部分单独显示“超收金额”，不得用超过100%的进度条破坏布局。

### 收款明细抽屉

| 区域 | 字段 |
|---|---|
| 明细表 | 支付时间、收款金额、支付渠道、三方流水号、支付状态。 |
| 汇总 | 成功支付笔数、累计支付、累计退款、净收款、应收金额、剩余待收。 |

刷新必须调用服务端案件收款汇总/流水接口；不能只读取前端缓存。到账和退款结果只更新收款进度，不自动修改案件状态、追责结果或结案状态。

## 6.5 分期待还款

1. 展示结案信息、催记和案件详情三个区域。
2. 支持更新每期还款进度、上传凭证和记录备注。
3. 还款计划更新不得修改原结案金额；每笔更新写入还款历史。

7. 🔵 待确认：分期待还款页是否增加“计划进度”和“实际收款进度”双进度展示，以及一笔到账应按哪一期分配；当前原型仅同步动态收款码入口。

### H5提交结案

在提交结案之前，用户可通过"保存案件"按钮将当前填写的追责结果、金额、附件和备注保存至服务端，不触发人脸验证和审核流程。

1. 若 `h5_close_face_enabled=false`，沿用原结案校验并提交。
2. 若启用，先检查结案验证锁定状态，再进行人脸验证。
3. 验证通过后才提交结案请求；失败不生成结案结果。
4. 达到失败上限后根据 `h5_close_failure_action` 保留登录或退出。
5. 地理位置由当前IP/基站位置自动识别，页面只读展示，用户不能输入或修改。
6. 页面显示“该字段提交时隐藏，只能查看，不能编辑”；真实位置结果由可信终端能力或服务端记录。

## 6.8 我的

展示实名姓名、账号、团队、角色和任务统计，提供资料查看、修改密码及退出。修改敏感账号信息需重新认证并记录操作日志。

# 第七章 跨端业务流程与同步规则

## 7.1 案件生成、流转与人员分配

```text
售后系统创建售后订单
→ 追责服务生成案件（待委案）
→ 后台选择案件状态和流转目标
→ 分配团队并生成阶段时限
→ 前台案件管理·待分配显示
→ 组长分配追责人员
→ 我的案件/H5同步显示
```

| 数据项 | 同步方向 | 触发时机 | 同步规则 |
|---|---|---|---|
| 案件基础信息 | 售后系统→追责系统 | 转售后/创建案件 | 创建案件快照，保留源订单号。 |
| 团队 | 后台→前台 | 团队流转成功 | 更新 `team_id`，生成团队待分配任务。 |
| 负责人 | 前台→我的案件/H5 | 人员分配成功 | 更新 `owner_id`，移出待分配。 |
| 时限 | 后台/前台→任务 | 每次流转或分配 | 保存阶段开始、截止和超时策略。 |
| 待办角标 | 服务端→菜单/Tab | 列表查询或状态变化 | 使用同一统计接口，禁止DOM互相抄值。 |

## 7.2 催记与历史同步

```text
前台/H5/案件详情新增催记
→ 校验案件可操作状态
→ 上传附件
→ 保存催记记录
→ 追加案件历史进程
→ 售后系统/相关详情页同步展示
```

已提交催记不得直接覆盖；修正错误应新增“更正记录”并引用原记录ID。

## 7.3 两级审核与后续流转

```text
追责员提交处理结果
→ 前台组长初审
   ├─ 驳回：退回提交人
   └─ 通过：进入后台终审
→ 后台终审
   ├─ 驳回：退回提交人
   ├─ 继续处理：进入后台待分配对应阶段
   └─ 结案：固化结案快照并生成回访订单
```

审核通过和驳回必须采用乐观锁或状态版本号，避免同一申请被重复处理。

## 7.4 结案手机号与回访

| 阶段 | 输入 | 输出 |
|---|---|---|
| 打开结案弹窗 | `case_id`、用户手机号权限 | 案值、手机号展示值、是否脱敏。 |
| 提交结案 | 结果、金额、手机号修改状态；系统识别当前IP/基站位置 | `follow_up_phone`、`phone_modified`、系统位置结果、结案快照。 |
| 审核 | 结案快照 | 前后台审核只读展示追责电话。 |
| 生成回访 | 终审结案成功 | 唯一回访订单，初始`待回访`。 |
| 管理回访 | 状态、记录、说明、附件 | 追加历史、回访时间、当前状态。 |

## 7.5 敏感信息授权

| 步骤 | 服务端要求 |
|---|---|
| 创建申请 | 校验申请人对案件具备基础访问权；记录来源和字段集合。 |
| 查询审批 | 按审核人权限返回申请；敏感值本身仍保持脱敏。 |
| 通过 | 保存申请人、案件、字段、有效期、审核人和时间。 |
| 读取详情 | 每次请求实时校验授权是否有效；未授权不返回完整值。 |
| 到期/收回 | 立即使授权失效；已打开页面下一次请求或心跳后重新脱敏。 |

## 7.6 共案处理

```text
识别共案组
→ 展示组成员和历史归属
→ 用户选择团队/负责人/流转目标
→ 首次确认
→ 共案二次确认（各共案订单以复选框展示，默认全选，可单独取消）
→ 服务端重新校验勾选成员状态
→ 同一事务更新已勾选成员
→ 返回成功项与跳过项
```

## 7.7 IM消息

1. 打开详情时，先按 `applicant_id + case_id + im_messages` 校验有效授权；未授权不返回消息正文和附件真实地址。
2. 交易售后群和卖家售后群支持发送，交易群只读；发送权限与读取敏感权限分别校验。
3. 消息实体以 `case_id + group_type + message_id` 唯一定位；同案同群跨菜单实时同步，服务端保存发送人、身份、时间、内容、附件及撤回状态。

## 7.8 动态收款、支付回调与退款

```text
前台/H5请求生成动态收款码
→ 服务端生成 payment_code_id 和30分钟有效期
→ 客户支付
→ 支付渠道回调（幂等）
→ 生成 PaymentTransaction
→ 更新案件支付汇总
→ H5刷新收款进度
→ 前台提交全额/部分退款
→ 后台确认或驳回
   ├─ 驳回：保留支付结果，前台可重新申请
   └─ 审核通过：退款状态更新为“退款处理中”
                  ├─ 渠道成功：退款成功 → 更新累计退款与案件净收款汇总
                  └─ 渠道失败：退款失败 → 保持支付结果和净收款，进入重试/人工处理
```

| 数据项 | 触发时机 | 同步规则 |
|---|---|---|
| 动态码 | 生成/重新生成 | 关联 `case_id + payment_code_id`，服务端时间控制有效期。 |
| 支付流水 | 支付成功回调 | 以支付渠道事件和三方流水号幂等生成，前端不得自行创建成功流水。 |
| 案件收款汇总 | 支付或退款完成 | 按案件实时聚合，不与案件处理状态互相覆盖。 |
| 退款申请 | 前台提交 | 固化申请时交易、金额、原因、申请人和时间。 |
| 退款审核 | 后台处理 | 固化审核人和时间；驳回不改变实收，审核通过先进入“退款处理中”，最终由渠道结果更新为“退款成功”或“退款失败”。 |

## 7.9 案件标签同步

```text
后台维护 TagDefinition
→ 前台我的案件管理 CaseTag
→ 前台/后台案件管理同步标签列、悬浮气泡和筛选项
```

标签多选筛选采用“匹配任一所选标签（OR）”。删除标签时应在事务中停用或解除案件关联并保留审计；生产环境建议逻辑删除，避免历史操作记录失去标签语义。

## 7.10 历史售后快照

历史售后记录在阶段完成或售后责任归属固化时创建，至少包含 `case_id`、`order_id`、团队、负责人和当时完成状态。后续团队/负责人变化不得覆盖历史快照。列表“历史售后次数”直接由有效快照条数派生，不保存第二份可独立修改的统计事实。

# 第八章 状态与业务规则

## 8.1 状态维度隔离

| 维度 | 字段建议 | 作用 | 是否互相自动覆盖 |
|---|---|---|---|
| 案件状态 | `case_status` | 表示案件业务类型。 | 否 |
| 追责状态 | `responsibility_status` | 表示处理阶段。 | 否 |
| 追责结果 | `case_result` | 表示当前追责结果。 | 否 |
| 包赔状态 | `guarantee_status` | 表示包赔业务状态。 | 否 |
| 回访状态 | `follow_up_status` | 表示结案后回访结果。 | 否 |
| 审批状态 | `approval_status` | 表示申请处理进度。 | 否 |
| 权限申请状态 | `request_status` | 表示敏感授权申请进度。 | 否 |
| 支付状态 | `payment_status` | 表示单笔交易的支付/退款结果。 | 否 |
| 退款申请状态 | `refund_status` | 表示退款申请审核和执行进度。 | 否 |

## 8.2 案件状态枚举

| 状态 | 说明 |
|---|---|
| 换号换绑 | 通过更换绑定信息处理案件。 |
| 追回退款 | 以追回款项为目标。 |
| 平台赔付 | 平台先行赔付后追偿。 |
| 买家恶意 | 买方存在疑似恶意行为。 |

## 8.3 追责状态枚举与流转

```text
待委案
  → 一手处理中
  → 一手处理完成
     ├→ 二手处理中
     │   → 二手处理完成
     │      ├→ 线下处理中
     │      │   → 线下处理完成
     │      └→ 已结案
     └→ 已结案
```

| 当前状态 | 可执行动作 | 典型目标状态 |
|---|---|---|
| 待委案 | 流转团队 | 一手处理中、线下处理中（按规则） |
| 一手处理中 | 提交处理、回退 | 一手处理完成、待委案 |
| 一手处理完成 | 审核、继续流转、结案 | 二手处理中、已结案 |
| 二手处理中 | 提交处理、回退 | 二手处理完成、一手处理完成 |
| 二手处理完成 | 审核、线下、结案 | 线下处理中、已结案 |
| 线下处理中 | 外访结案、回退 | 线下处理完成、上一合法状态 |
| 线下处理完成 | 审核、结案 | 已结案 |
| 已结案 | 查看、回访 | 终态，不允许再次流转 |

> 已确认：`线下处理中`、`线下处理完成` 已纳入正式追责状态机；一手处理完成、二手处理完成均允许按合法路径直接结案。所有列表、审核、外访和流转页面必须读取同一状态配置源。

## 8.4 追责结果枚举

| 状态 | 说明 | 可流转至 |
|---|---|---|
| —（待定） | 尚未形成结果。 | 分期还款中、已追回、未追回 |
| 分期还款中 | 已形成分期计划。 | 已追回、未追回 |
| 已追回 | 款项追回完成。 | 终态 |
| 未追回 | 暂未追回。 | 分期还款中、已追回 |

> 🔵 待确认：结案弹窗还包含“还号换绑”，需明确其是结案结果、案件状态，还是同时写入两个字段，并给出唯一映射表。
>
> 初步确认：不做修改


## 8.5 包赔状态

`未购买、失效、在保、骗保、自费协追`。状态变化需要附件和说明；“失效/骗保”是否进入审批流由后台审批流配置决定。

## 8.6 回访状态

`待回访、已完成、态度不佳、沟通不及时、工作人员违规、隐私泄露、客户投诉`。后五项异常状态由状态值直接判断，不再保存 `special_flag` 或 `special_type`。

## 8.7 权限申请状态

```text
待审批 ──通过──→ 已通过 ──到期/收回──→ 已失效
   └────拒绝──→ 已拒绝 ──重新申请──→ 新的待审批记录
```

## 8.8 人脸验证结果与场景

| 维度 | 枚举 |
|---|---|
| 验证结果 | 验证通过、验证失败、用户取消、验证超时、系统异常 |
| 场景 | 首次采集后重新登录、普通登录、会话到期后登录、主动退出后登录、强制退出后登录、更换设备后登录、提交结案前校验 |

## 8.9 支付与退款状态

| 维度 | 状态 | 说明 |
|---|---|---|
| 支付状态 | 待支付、已支付、部分退款、已退款、支付失败、已关闭 | 单笔支付订单或交易结果；不替代案件状态。 |
| 退款申请状态 | 未申请（派生展示）、待审核、已驳回、退款处理中、退款成功、退款失败 | 表示一轮退款申请从提交、审核到渠道执行结果的完整状态；“未申请”表示当前不存在退款申请记录。 |

```text
未申请 → 待审核
待审核 → 已驳回 → 新申请（新记录）
待审核 → 退款处理中
退款处理中 → 退款成功
退款处理中 → 退款失败 → 幂等重试/人工处理
```

> 已确认：生产退款流程采用“待审核—退款处理中—退款成功/退款失败”。后台审核通过只代表允许发起退款，不代表资金已经退回；只有渠道返回成功后才能更新累计退款、净收款及 `payment_status`。
>
> `payment_status` 使用：待支付、已支付、部分退款、已退款、支付失败、已关闭。`refund_status` 使用：待审核、已驳回、退款处理中、退款成功、退款失败。“部分退款”只表示交易累计退款结果，不作为单次退款申请状态。
> 
> 🔵 待确认：原型同时存在 `transaction_status` 和 `payment_status`。建议统一使用 `payment_status` 作为单笔交易唯一状态，`transaction_status` 仅作为旧原型兼容字段，不应形成第二套状态源。

## 9.10 数据约束

1. `follow_up_phone` 与 `customer_phone` 必须独立存储，禁止数据库触发器互相覆盖。
2. 结案终审成功后，按 `case_id + close_id` 幂等生成一条回访订单。
3. 回访历史只允许INSERT，不允许业务端UPDATE/DELETE。
4. 敏感字段加密存储，列表搜索使用安全索引或受控解密服务。
5. 案件状态更新必须携带 `version`，冲突返回409。
6. 案件快照、回访快照、人脸案件快照生成后不随后续案件转移修改。
7. `third_party_transaction_id + payment_channel` 建议建立唯一约束；支付回调必须幂等。
8. 单笔交易累计已完成退款金额不得超过成功支付金额；金额使用整数分或高精度Decimal。
9. 同一交易同时最多存在一条活动中的退款申请；驳回后重提应创建新申请记录并保留旧记录。
10. `CaseTag` 和历史售后快照不得修改案件状态；删除标签不得删除历史操作日志。
11. 流转资损写入 `CaseAssignment`/流转记录，不再仅属于结案记录；`loss_included=false` 时 `loss_amount` 的持久化口径见Q22。
12. 只有 `refund_status=succeeded` 才能增加交易累计退款并重新计算案件净收款；`processing`、`failed` 或 `rejected` 均不得改变实际资金汇总。

### 提交结案

```json
{
  "case_id": "CS-20260706-001",
  "case_result": "已追回",
  "case_amount": 12800,
  "recovered_amount": 12800,
  "follow_up_phone": "13812345678",

  "installments": [],
  "attachment_ids": [],
  "remark": ""
}
```

无完整手机号权限且未修改脱敏号码时，前端应省略 `follow_up_phone` 或明确发送 `phone_modified=false`；服务端从案件底层手机号解析最终值。

`location_source` 和 `location_text` 不接受用户自由输入，应由可信终端能力或服务端在提交时生成并写入结案记录。

### 案件结案流转

```json
{
  "flow_target": "分配至二手团队",
  "loss_included": true,
  "loss_amount": 9800,
  "remark": "流转至二手团队并记录资损决策"
}
```

四种流转目标都提交明确的 `loss_included`；`loss_amount` 必须为不小于0的合法金额。当前案件金额和已追回金额由服务端返回，前端只作为参考展示。`loss_included=false` 时是否保存候选 `loss_amount` 尚未定案，见Q22。

### 生成动态收款码

```json
{
  "case_id": "WA-20260708-001",
  "amount": 1280000,
  "source": "h5",
  "source_page": "h5_tasks"
}
```

响应至少包含 `payment_code_id`、安全码载荷/支付地址、`generated_at`、`expires_at` 和服务端当前时间。金额示例以“分”为单位；接口最终单位必须全域统一。

```json

}
```

服务端需校验交易归属、支付成功、当前可退金额、活动退款申请、操作权限和幂等键；前端计算的退款类型仅用于展示，最终由服务端按金额判断。

## 10.3 接口通用规则

1. 写接口必须支持幂等键 `Idempotency-Key`。
2. 业务错误返回可识别错误码、用户文案和最新状态。
3. 列表统一分页、排序、数据范围和脱敏策略。
4. 所有时间使用带时区ISO 8601存储，页面按Asia/Shanghai展示。
5. 金额使用整数分或高精度Decimal，禁止浮点数。
6. 附件接口不返回本地文件路径，使用短期签名URL。
7. 支付回调和退款结果回调必须验证签名并幂等；后台审核通过只将退款更新为“退款处理中”，前端页面状态不能作为最终资金结果依据。
8. 交易流水搜索参数建议为 `search_field`、`keyword`、`payment_channel`、`page`、`page_size`，并由服务端执行数据权限和分页。
9. 所有资金金额统一使用整数分或高精度Decimal，累计退款不得超过实付金额。
10. 标签、历史售后和退款审核的新增/删除/状态变化必须记录操作日志。

| 超额退款 | 单笔交易累计完成退款超过实付金额必须为0。 |
| 未授权IM正文返回 | 无 `im_messages` 授权时返回真实正文或附件地址必须为0。 |

# 第十三章 用户故事与验收标准

## 13.1 Epic假设

将订单转案、团队流转、人员分配、执行记录、两级审核、结案回访、敏感权限和登录安全纳入统一三端平台，可减少跨页面和跨团队的信息断层，提高案件分配、审核和回访闭环效率，并降低越权访问和不可追溯风险。成功与否通过案件闭环率、分配/审核及时率、回访完成率及零越权泄露等指标验证。

## 13.2 Story 1：团队内分配案件

作为团队管理员，需求在案件管理的待分配页签为案件选择追责人员，以便案件进入具体人员的作业队列。

**验收标准：**

- [ ] 前台不显示独立分案管理菜单，案件管理包含团队案件和待分配。
- [ ] 待分配筛选、列表、单件和批量分配可用。
- [ ] 分配时团队、人员和处理时效必填。
- [ ] 成功后案件移出待分配并进入目标人员我的案件。
- [ ] 菜单和Tab待分配角标同步更新。
- [ ] 有共案时“关联案件”列显示去重后的“X个关联”，无共案时显示“—”。
- [ ] 列表关联数量、分配提示和二次确认使用同一版本的共案数据。
- [ ] 无权限、状态变化或重复分配时不写入数据。

## 13.3 Story 2：共案安全分配

作为管理员，我希望分配共案时看到关联案件及历史团队/负责人并二次确认，通过复选框选择需同步分配的共案订单，以避免拆散同一追责目标。

**验收标准：**

- [ ] 单件存在共案时首个弹窗展示数量、编号、历史团队和负责人。
- [ ] 点击确认后弹出二次确认，共案订单以复选框列表展示，默认全部勾选。
- [ ] 两处弹窗的共案订单编号完全一致。
- [ ] 二次确认前不写入任何分配数据。
- [ ] 无共案订单不展示共案提示，也不触发共案二次确认。
- [ ] 服务端提交时重新校验共案成员状态并返回跳过原因。
- [ ] 共案同步不覆盖成员自身金额、催记、结果或历史。

## 13.4 Story 3：后台流转案件

作为后台运营，我希望将案件流转至一手、二手、线下团队或结案，以推动案件进入下一合法阶段。

**验收标准：**

- [ ] 流转弹窗案件状态与状态机四个枚举一致。
- [ ] 流转目标固定为一手、二手、线下、结案四类。
- [ ] 非法目标不可提交。
- [ ] 四种流转目标下均在目标下方常态展示“是否计入资损”的“是/否”单选，默认“否”。
- [ ] 资损金额默认带入案件金额，所有目标及“是/否”状态下均允许修改，切换流转目标不重置。
- [ ] 资损区域以只读灰字展示当前案件金额和已追回金额。
- [ ] 批量流转按选中案件汇总默认资损金额。
- [ ] 状态并发变化时返回冲突，不覆盖最新状态。

## 13.5 Story 4：追责员记录案件过程

作为追责员，我希望记录每次联系及附件，以便后续审核人员完整了解案件过程。

**验收标准：**

- [ ] 联系时间、结果、内容必填，附件可选。
- [ ] 成功后催记追加至案件历史和详情。
- [ ] 已提交记录不可直接覆盖。
- [ ] 已结案或无操作权时只能查看。

## 13.6 Story 5：提交结案与确认手机号

作为追责员，我希望在提交结案时确认追偿目标手机号，以便审核和回访使用正确联系方式。

**验收标准：**

- [ ] 手机号初始值与当前案件详情展示值一致。
- [ ] 切换案件后不保留上一案件号码。
- [ ] 有权限用户可保留或编辑完整号码。
- [ ] 无权限用户未修改脱敏号码时，服务端使用案件底层号码。
- [ ] 编辑后必须输入完整有效号码，不允许星号或非数字字符。
- [ ] 保存至 `follow_up_phone`，不修改 `customer_phone`。
- [ ] 前后台审核的追责电话与回访管理联系电话同源。
- [ ] 前台与H5地理位置均由当前IP/基站位置自动识别，只能查看、不能编辑。
- [ ] 结案请求不接受用户自行填写的位置文本，服务端保存可信识别结果。

## 13.7 Story 6：两级审核

作为组长/后台审核人员，我希望核对追责结果、催记和联系电话并通过或驳回，以确保结案结果合规。

**验收标准：**

- [ ] 初审通过后进入后台终审，驳回退回原提交人。
- [ ] 追责电话只读展示 `follow_up_phone`。
- [ ] 驳回备注必填，通过备注选填。
- [ ] 重复审核被服务端拒绝。
- [ ] 审核结果写入案件历史和操作日志。

## 13.8 Story 7：追加回访记录

作为回访人员，我希望管理结案回访并追加历史记录，以便保留每次客户反馈。

**验收标准：**

- [ ] 终审结案后幂等生成待回访订单。
- [ ] 联系电话优先使用 `follow_up_phone`。
- [ ] 主列表回访记录列只显示“管理”。
- [ ] 管理弹窗基础信息为紧凑只读文本。
- [ ] 回访状态位于回访记录上方，状态和记录必填。
- [ ] 提交时间自动写入，历史只可追加。
- [ ] 提交后列表、统计更新并关闭弹窗。
- [ ] 顶部仅保留“待回访、已完成、异常情况”三张统计卡，并按统一状态字段实时统计。

## 13.9 Story 8：申请查看敏感信息

作为案件处理人员，我希望申请当前案件所需敏感字段，以便在授权范围内完成联系和核验。

**验收标准：**

- [ ] PC详情可全量、单字段或IM模块申请；H5可一次申请六类案件敏感信息。
- [ ] 申请处理中不跳转、不重复提交，并显示处理状态。
- [ ] 后台可通过、拒绝、设置有效期和收回。
- [ ] H5通过后仍默认收起，点击模块一键展开才显示。
- [ ] 未授权时接口不返回完整敏感值。
- [ ] 未授权 `im_messages` 时接口不返回三个群聊的真实正文或附件地址。
- [ ] 到期或收回后再次请求恢复脱敏。

## 13.10 Story 9：登录与结案人脸验证

作为安全管理员，我希望配置会话时长、验证场景和失败保护，以减少账号冒用。

**验收标准：**

- [ ] 会话时长、失败上限、窗口和锁定时长只接受大于0的整数。
- [ ] 普通登录和H5结案验证可分别启停。
- [ ] 计次和不计次原因符合配置说明。
- [ ] 达到登录上限后暂时禁止登录。
- [ ] 结案失败不生成结果，并按配置保留会话或退出。
- [ ] 验证记录只展示当前账号，失败角标与未读失败数量一致。

## 13.11 Story 10：跨页面IM同步

作为案件处理人员，我希望在交易售后群和卖家售后群发送消息，并在其他菜单的同案详情看到消息。

**验收标准：**

- [ ] 两个售后群支持按钮和Enter发送。
- [ ] 交易群保持只读。
- [ ] 未获 `im_messages` 权限时三个群聊均不可读、不可操作；授权通过后读取能力同时生效。
- [ ] 消息按案件和群类型隔离。
- [ ] 发送人、身份、时间和内容完整记录。
- [ ] 无发送权限或案件已关闭时按配置禁止发送。

## 13.12 Story 11：外访移动作业

作为外访员，我希望在H5查看任务、签到取证并提交结果，以便完成线下处理闭环。

**验收标准：**

- [ ] 外访申请通过后生成目标人员可见任务。
- [ ] 地址按敏感权限展示。
- [ ] 不同外访结果展示对应附件和金额字段。
- [ ] 提交后进入审核，审核通过才标记完成。
- [ ] 附件、位置和操作时间写入历史。

## 13.13 Story 12：生成动态收款码

作为追责员，我希望从前台或H5为当前案件生成限时收款码，以便客户付款并准确关联案件。

**验收标准：**

- [ ] 前台我的案件及H5首页、我的案件、分期待还款均有生成入口。
- [ ] 弹窗展示案件编号、金额、`payment_code_id`、生成时间、失效时间和倒计时。
- [ ] 动态码有效期30分钟，过期后必须重新生成。
- [ ] 服务端签发并校验码值，客户端不能延长有效期。
- [ ] 生成或过期不修改案件状态。

## 13.14 Story 13：查看多笔收款进度

作为H5追责员，我希望在案件卡片查看多次付款汇总并打开明细，以便快速判断实际已收和剩余金额。

**验收标准：**

- [ ] 卡片展示未收款、部分收款、已收齐或超额收款，退款另行提示。
- [ ] 净收款等于成功支付减已完成退款，退款审核中不提前扣减。
- [ ] 多笔支付在卡片汇总，明细抽屉逐笔展示时间、金额、渠道、三方流水和状态。
- [ ] 付款比例最高显示100%，超收金额单独显示。
- [ ] 刷新调用服务端最新汇总并显示最后更新时间/新到账。
- [ ] 收款变化不自动修改案件状态或触发结案。

## 13.15 Story 14：申请和审核退款

作为追责员，我希望对一笔已支付流水提交全额或部分退款；作为后台审核人员，我希望确认或驳回申请。

**验收标准：**

- [ ] 前后台交易流水字段、搜索口径和同一笔数据保持一致。

- [ ] 提交后进入待审核，前端不能直接改变资金状态。
- [ ] 后台只处理待审核申请，确认和驳回均记录操作人与时间。
- [ ] 驳回不修改实收，前台恢复退款入口并以新申请记录重新提交。
- [ ] 审核通过后进入“退款处理中”，不得直接显示退款成功或扣减净收款。
- [ ] 渠道成功后更新为“退款成功”，并按累计退款结果将支付状态更新为“部分退款”或“已退款”。
- [ ] 渠道失败后更新为“退款失败”，保留原支付状态和净收款，并支持幂等重试或人工处理。
- [ ] 单笔交易累计完成退款不超过实付金额。

## 13.16 Story 15：维护和使用案件标签

作为后台管理员，我希望维护标签字典；作为案件处理人员，我希望管理和筛选案件标签，以便快速识别风险特征。

**验收标准：**

- [ ] 删除前二次确认；删除后解除案件关联但保留审计。

- [ ] 下拉单列可滚动且不被表格遮挡。

作为案件处理或管理人员，我希望查看当前案件历次售后归属和完成状态，并在列表看到次数。

## 15.1 依赖

| 类型 | 依赖 | 阻塞内容 |

## 15.2 风险与缓解

| 风险 | 类型 | 影响 | 缓解措施 |
|---|---|---|---|
| 多套案件编号映射 | 可行性 | 前后台串案或手机号错配。 | 全端统一`case_id`，移除原型静态映射。 |
| 状态枚举不一致 | 可行性 | 非法流转、页面筛选遗漏。 | 上线前建立唯一状态字典；页面只读取服务端配置。 |
| 敏感值下发后前端隐藏 | 安全 | 可通过开发者工具泄露。 | 未授权时服务端不下发完整值。 |
| 共案并发流转 | 数据一致性 | 同组案件被分至不同人员。 | 组版本号、事务锁、逐项结果和幂等键。 |
| 结案重复生成回访 | 数据一致性 | 重复联系客户。 | `case_id+close_id`唯一约束。 |
| 人脸误拒/服务不可用 | 可用性 | 合法人员无法工作。 | 区分计次原因，设置降级审批和服务监控。 |
| 附件内容不合规 | 安全/合规 | 恶意文件或隐私泄露。 | 文件头校验、扫描、访问签名、水印和留存策略。 |
| 指标口径不一致 | 价值 | 看板无法支持决策。 | 数据字典、口径负责人和上线前基线核对。 |
| 支付回调重复/乱序 | 资金一致性 | 重复入账或汇总倒退。 | 验签、幂等键、渠道事件版本和账务对账。 |
| 退款审核成功但渠道执行失败 | 资金一致性 | 页面显示已退但客户未到账。 | 审核状态与资金执行状态分离，异步重试并人工告警。 |
| 超额或多次付款归属错误 | 资金一致性 | 错案、错期核销或错误退款。 | 强制关联 `payment_code_id/case_id`，建立未分配款和人工调账流程。 |
| 标签被物理删除 | 可追溯性 | 历史记录无法解释当时风险判断。 | 生产环境逻辑删除并保留标签名称快照。 |
